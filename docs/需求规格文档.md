# GitHub项目智能分析 - 需求规格文档

## 1. 项目概述

### 1.1 项目名称
GitHub项目智能分析（GitHub Project Intelligent Analyzer）

### 1.2 项目背景
中国开发者在阅读和理解GitHub上的英文项目时面临两大障碍：
1. **语言障碍**：README等文档为英文，阅读效率低
2. **技术理解障碍**：难以快速把握项目架构、技术栈和核心价值

现有工具功能分散，缺乏一站式解决方案。

### 1.3 项目目标
构建一个AI驱动的Web应用，帮助中国开发者快速理解和评估GitHub项目，主要服务于**技术选型调研**场景。

### 1.4 核心价值主张
- **30秒快速概览**：输入GitHub链接，立即获取项目关键信息
- **深度分析模式**：深入理解项目架构和实现细节
- **中文友好**：所有分析结果以中文呈现，保留原始Markdown格式

## 2. 用户分析

### 2.1 目标用户
- 中国开发者（初级/中级/高级）
- 技术管理者（进行技术选型）
- 开源爱好者（探索新项目）

### 2.2 用户场景
| 场景 | 描述 | 优先级 |
|------|------|--------|
| 技术选型调研 | 快速判断一个项目是否值得深入学习或采用 | P0 |
| 学习开源项目 | 快速上手一个新的开源项目 | P1 |
| 竞品分析 | 分析竞品项目的技术实现 | P1 |

### 2.3 用户旅程
```
输入GitHub URL → 选择分析模式 → 等待分析 → 查看结果 → 导出报告
```

### 3.2 功能详细说明

#### 3.2.1 README全文翻译
**输入**：GitHub仓库URL
**处理流程**：
1. 通过GitHub API获取README原始内容
2. 调用AI模型进行翻译（保留Markdown格式）
3. 处理特殊元素：代码块、链接、图片、表格

**输出要求**：
- 保留原始Markdown格式
- 代码块内容不翻译
- 链接保持原始URL
- 图片链接保持不变

**示例输入**：`https://github.com/facebook/react`
**示例输出**：
```markdown
# React

React 是一个用于构建用户界面的 JavaScript 库。

## 安装

​```bash
npm install react react-dom
```

## 示例

...（翻译后的完整README）
```

#### 3.2.2 项目一句话摘要
**输入**：GitHub仓库URL
**处理流程**：
1. 获取README、description、topics等元数据
2. 分析项目核心功能和价值
3. 生成简洁的中文摘要

**输出要求**：
- 长度：15-30个汉字
- 包含：项目类型 + 核心功能 + 目标用户
- 风格：技术准确、简洁明了

**示例**：
- React：「用于构建用户界面的声明式JavaScript库」
- Vue：「渐进式JavaScript框架，用于构建现代Web界面」

#### 3.2.3 技术栈分析
**输入**：GitHub仓库URL
**处理流程**：
1. 分析package.json、requirements.txt等依赖文件
2. 检测编程语言分布
3. 识别框架和库
4. 分类整理技术栈

**输出格式**：
​```json
{
  "languages": [
    {"name": "JavaScript", "percentage": 85},
    {"name": "TypeScript", "percentage": 15}
  ],
  "frameworks": [
    {"name": "React", "version": "18.2.0", "category": "前端框架"},
    {"name": "Next.js", "version": "13.0", "category": "全栈框架"}
  ],
  "tools": [
    {"name": "Webpack", "category": "构建工具"},
    {"name": "Jest", "category": "测试框架"}
  ],
  "databases": [],
  "cloud_services": []
}
```

#### 3.2.4 技术架构分析（P1）
**输入**：GitHub仓库URL
**处理流程**：
1. 分析目录结构
2. 识别核心模块和依赖关系
3. 检测设计模式
4. 生成架构描述

**输出格式**：
```markdown
## 项目架构

### 目录结构
```
src/
├── components/     # UI组件
├── hooks/          # 自定义Hook
├── utils/          # 工具函数
└── index.js        # 入口文件
```

### 核心模块
1. **组件系统**：基于React组件化架构
2. **状态管理**：使用Context API
3. **路由系统**：Next.js文件系统路由

### 设计模式
- 组件模式
- Hooks模式
- 发布-订阅模式
```

**处理流程**：
1. 获取最近N个Issues（默认100个）
2. 分析Labels分布
3. 计算活跃度指标
4. 识别常见问题类型

**输出格式**：

#### 3.2.7 项目代码问答（P1.5 - RAG方案）
**输入**：GitHub仓库URL + 用户自然语言问题（支持中文）
**技术方案**：RAG（检索增强生成）

**处理流程**：
1. **代码索引阶段**（首次分析时执行）：
   - 克隆/获取项目代码
   - 解析代码文件（支持主流编程语言）
   - 代码分块（按函数/类/文件级别）
   - 使用Embedding模型生成向量
   - 存储到向量数据库（ChromaDB）

2. **问答阶段**：
   - 用户输入问题（中文/英文）
   - 问题向量化
   - 检索相关代码片段（Top-K）
   - 构建Prompt（问题 + 检索到的代码上下文）
   - 调用LLM生成中文回答
   - 返回答案 + 引用的代码位置

**功能特性**：
| 特性 | 说明 |
|------|------|
| 中文问答 | 用户用中文提问，AI用中文回答 |
| 代码引用 | 回答中包含相关代码片段和文件路径 |
| 上下文理解 | 支持多轮对话，理解上下文 |
| 预设问题 | 提供常见问题模板（快速上手） |
| 会话管理 | 每个仓库独立会话，支持历史记录 |

**预设问题模板**：
- 「这个项目的核心功能是什么？」
- 「如何快速上手使用这个项目？」
- 「项目的主要模块有哪些？它们之间是什么关系？」
- 「这个项目使用了哪些设计模式？」
- 「如何为这个项目贡献代码？」
- 「项目的安全机制是如何实现的？」

**输出格式**：
```json
{
  "answer": "这个项目使用了观察者模式来处理事件...",
  "references": [
    {
      "file": "src/events/EventEmitter.ts",
      "line_start": 45,
      "line_end": 67,
      "code": "class EventEmitter {\n  private listeners: Map<string, Function[]>...\n}"
    }
  ],
  "confidence": 0.85,
  "session_id": "session_abc123"
}
```

**限制条件**：
- 单次对话最多10轮
- 每个仓库索引文件数上限：500个
- 单个文件最大：100KB
- 支持的文件类型：主流编程语言（.py, .js, .ts, .java, .go, .rs, .cpp, .c, .h）

#### 3.2.8 Claude Code Skill评估（P1.8）
**输入**：GitHub仓库URL
**处理流程**：
1. 检测项目是否为Claude Code Skill（识别SKILL.md文件）
2. 解析Skill结构和配置
3. 分析四个维度并生成评估报告
4. 计算综合推荐指数

**评估维度**：

**1. 兼容性和使用门槛**
| 检查项 | 说明 |
|--------|------|
| Skill格式规范 | 是否遵循标准SKILL.md格式 |
| 依赖声明 | 是否清晰声明依赖项 |
| 配置复杂度 | 是否需要额外配置步骤 |
| Claude版本兼容 | 是否声明支持的Claude版本 |

**2. 维护活跃度**
| 指标 | 权重 | 说明 |
|------|------|------|
| 最近更新时间 | 30% | 3个月内更新=高，6个月=中，>6个月=低 |
| Issue响应速度 | 25% | 平均响应时间 |
| 维护者活跃度 | 25% | 维护者最近提交频率 |
| 社区参与度 | 20% | Star/Fork/PR数量 |

**3. 功能完整性**
| 检查项 | 说明 |
|--------|------|
| 文档完整度 | 是否有README、使用示例 |
| 功能覆盖 | 覆盖多少场景 |
| 错误处理 | 是否考虑异常情况 |
| 可扩展性 | 是否支持自定义配置 |

**4. 安全风险**
| 风险类型 | 检查方式 |
|----------|----------|
| 外部脚本执行 | 是否调用外部脚本/API |
| 敏感权限 | 是否请求文件系统/网络访问 |
| 代码注入风险 | 是否有动态代码执行 |
| 数据泄露风险 | 是否发送数据到外部服务 |

**输出格式**：

## 4. 非功能需求

### 4.1 性能要求
| 指标 | 目标值 |
|------|--------|
| 快速概览响应时间 | < 30秒 |
| 深度分析响应时间 | < 2分钟 |
| 并发用户数 | 支持100+ |
| API响应时间 | < 500ms（不含AI处理） |

### 4.2 可用性要求
- 界面简洁直观，无需学习成本
- 支持移动端访问
- 提供清晰的加载状态和进度提示
- 错误信息友好且可操作

### 4.3 可靠性要求
- 系统可用性 > 99%
- 分析失败时提供重试机制
- AI模型调用失败时优雅降级

### 4.4 安全要求
- GitHub API Token安全存储
- 用户输入验证和消毒
- 防止API滥用（速率限制）
- 敏感信息不记录日志

## 5. 系统约束与外部依赖

### 5.1 外部依赖
| 依赖 | 用途 | 约束 |
|------|------|------|
| GitHub API | 获取仓库信息、README、Issues等 | 需要认证Token，有速率限制 |
| AI模型API | 翻译、摘要、分析、问答 | 需要API Key，按调用计费 |
| 向量数据库 | 代码问答功能（RAG） | 需要支持向量存储和检索 |

### 5.2 技术约束
- **部署形式**：Web应用（浏览器访问）
- **多模型支持**：需支持切换不同AI模型（Claude/GPT/Qwen等）
- **API优先**：需提供REST API，前端通过API调用后端
- **数据持久化**：需存储分析历史和问答会话

### 5.3 集成要求
- 前端与后端分离，通过API通信
- 后端需异步处理长时间任务（分析、索引）
- 需支持流式输出（问答场景）
